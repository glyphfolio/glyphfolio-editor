# Native egui adapter

`EditorPanel` is the configured, drop-in surface: toolbar, centered document, scrolling and optional status. Load `config::EditorConfig` from TOML or build it in Rust. It emits host save/diagnostic requests while dispatching editing actions through the original native input controller. The panel applies its palette locally; the embedding app keeps control of its other UI. See [configuration](../../docs/CONFIGURATION.md) and [visual results](../../docs/EDITOR_DESIGN.md).

`EditorWidget` embeds the original core editor through `NativeViewState`. Document bytes, selection, commands, revisions, history, and saved state belong to `glyphfolio-editor-core`. This adapter owns native event routing, disposable composition, projected geometry, painting, clipboard transport, and editable accessibility transport. It does not create a second editable document.

Source is the default presentation. Rich rendering requires both `enable_experimental_rich(true)` and `request_presentation(PresentationMode::Rich)` while platform qualification remains incomplete. Rich uses the CommonMark source projection, reveals the active semantic block, and applies heading typography, strong/emphasis/code font runs, links, quotes, lists, and fenced-code backgrounds. The host receives activated links through `take_activated_link()` and decides how to open them.

All geometry entering core actions uses canonical source byte coordinates. Piecewise projection maps and affinities handle folded syntax and transformed entities/escapes; displayed offsets are never submitted as source transactions. Switching presentation preserves the source selection and history. Scroll correction captures a source byte and local vertical offset, maps it through committed edits, and resolves it against the new projection instead of assuming Source and Rich block identities match.

The renderer shapes visible blocks with overscan and the caret's immediate neighbors. Source files and multiline Rich code fences use stable hard-line blocks. Derived shape and raster retention have explicit budgets in `glyphfolio-editor-layout`. `render_metrics()` reports actual work and string materialization separately. Source line reconciliation, projection construction, and the compatibility geometry bridge still scan/materialize complete strings after invalidation; bounded visible shaping is not a claim of fully bounded editing latency. A paragraph larger than 32 KiB with more than 512 style intervals explicitly falls back to Source before attributed shaping; `RenderMetrics.large_rich_source_fallback` and `rendered_presentation()` let the host explain this. The demo shows a visible notice. Source hard lines remain virtualized. This safeguards the current backend's pathological attributed-paragraph cost; it does not qualify giant Rich paragraphs. An enormous unbroken Source line still uses the explicit exact fallback and can require whole-block work.

Active IME preedit temporarily uses the Source presentation. Its overlay retains an explicit source replacement map; commit/cancel and deferred mode changes continue through the original composition session. The canonical source remains unchanged until commit. This temporary presentation limitation avoids treating provisional text as a second document or parsing it under a new document identity.

When accessibility is active, the adapter prepares complete projected text geometry so editable text actions can address offscreen content. An unchanged complete geometry Arc is reused across selection and viewport changes. This functional fallback can shape and retain the entire document; large-document accessibility performance is unqualified. Headless semantic/action tests establish controller behavior, not successful VoiceOver or other native screen-reader interaction.

The crate's tests cover source-mapped Rich actions, Unicode geometry, preedit ownership, full offscreen semantic geometry, Source/Rich scroll anchors, 10,001-line Source shaping, and a 10,000-line Rich code fence. Native IME, candidate-window placement, screen readers, clipboard ownership, GPU performance, and platform coverage require the separate feasibility/qualification evidence in the repository's `docs/` directory.
